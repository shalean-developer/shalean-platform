# Payment notification integrity — 16 October 2026

Owner request: fix misleading payment reminders, incomplete booking confirmations and failed office alerts. The owner selected `info@shalean.co.za` as the office inbox. Delivery follows isolated changes → regression checks → reviewed staging → production → reconciliation. No unrelated earnings work or historical payment corrections are included.

## Verified defects and sources

- Paystack Live had `/api/payment/webhook`, which returns 404 and has no application handler. The owner saved the correct `/api/paystack/webhook` destination. A valid signed delivery remains to be observed; browser GET 405 does not test delivery.
- Abandoned-checkout recovery and adaptive payment-link reminders independently sent requests for the same booking one second apart. Both relied on operational `pending_payment` without checking Paystack at dispatch.
- Deferred emails replayed stored payloads without rereading payment status; SMS fallback could follow an obsolete email attempt.
- Payment-confirmation orchestration selected `bookings.user_id`, absent from the current production schema, and ignored the query failure. The real row uses `customer_id`. The resulting sparse template showed Pending date/reference and omitted address/name.
- Missing `ADMIN_NOTIFICATION_EMAIL` prevented office notification. The owner explicitly chose the production fallback inbox above. Staging/local never inherit it.

## Implementation and acceptance

1. All current payment-link delivery paths and legacy recovery/expiry jobs read current booking/ledger evidence, verify the exact reference at Paystack, and reread the booking before sending. Confirmed paid, monthly, changed references, reversed or in-flight charges and uncertain lookups suppress payment requests. Actual send failures retain bounded retries; deferred eligibility outages retain queued work with capped backoff until recovery or link expiry; terminal expiry transitions remain retryable through gateway or transition outages. Reminder batches prioritize expiry time, stop taking work after four minutes, and skip timing delays to stay inside the cron lease. Abandoned checkout alone can recover a not-yet-initialized transaction after local ledger checks and Paystack’s explicit missing-transaction response (or no reference yet); gateway outages remain suppressed. See https://paystack.com/docs/api/errors/transaction/. Deferred workers claim at most five rows per invocation. Recurring fallback work is queued durably before its completion marker, and admin checkout reuse reports actual provider acceptance. Direct abandonment and legacy sends recheck after winning claims. Accepted recurring queue work is reused when repairing a failed fallback marker. No financial settlement is invented by this check.
2. Both first-reminder paths and legacy reminders share a database-unique claim in the existing notification idempotency table. The final reminder is a separate event. Legacy abandonment claims and existing adaptive reminder timestamps remain authoritative during rollout. Failed deliveries and pre-delivery exceptions release their claim; accepted sends retain the claim even if telemetry or persistence subsequently fails; claim errors suppress sending. Abandonment recovery sends SMS only after email is missing/fails.
3. Confirmation queries resolve the actual customer ownership column, include persisted customer name/contact, and report load failures rather than sending fabricated booking details. Existing row/snapshot presentation helpers and template variables remain canonical. A notification-only failed-job consumer replays paid confirmations after enrichment/delivery failures without replaying settlement, and worker replay does not enqueue duplicate recovery jobs. Retained confirmations use scheduled capped backoff so newer work remains eligible, and accepted SMS completes phone-only delivery. Retryable suppression of an initial admin payment link queues durable delivery work.
4. All office notification paths use one validated recipient resolver. Explicit environment configuration wins; the approved fallback is restricted to the production deployment. Multi-inbox delivery retains explicit To/Bcc handling.
5. `/api/payment/webhook` is a compatibility URL that re-exports the canonical POST handler. Outstanding Paystack retries to the previously configured URL retain exact signature/idempotency validation and use the same financial finalizer. The canonical saved URL remains `/api/paystack/webhook`.
